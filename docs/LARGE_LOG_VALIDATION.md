# 대용량 로그 검증

데스크톱 빌드의 성능 측정 조건과 결과, 검증 범위 및 한계를 정리한 문서입니다. 현재 코어를 기준으로 다시 실행할 수 있는 벤치마크 도구는 [`bench/`](../bench/README.md)에 있습니다.

## 기본 측정 환경

- **하드웨어 및 OS:** Apple M4 Mac mini(10코어, 16 GiB RAM) 및 Apple M5 Pro(15코어, 24 GiB RAM), macOS, Rust 1.99.0, Node.js 22
- **워크로드:** Android 2 : iOS 1 비율의 합성 로그(한글·이모지 포함), OS 파일 캐시에 적재된 warm 캐시 상태 기준

## 백엔드 엔진 처리량

엔진 API를 직접 호출해 1 ms 미만 간격으로 완료 상태를 폴링하며 측정한 결과입니다(M4 Mac mini 16 GiB, 단회 순차 측정).

| 작업 | 512 MiB LF (기존→개선) | 512 MiB CRLF (기존→개선) | 2 GiB LF (기존→개선) |
| --- | ---: | ---: | ---: |
| 인덱싱 완료 | 0.368 → 0.094 s | 0.339 → 0.095 s | 1.386 → 0.384 s |
| 레벨 E 필터 (집계 전) | 5.058 → 0.631 s | 5.073 → 0.632 s | 20.51 → 2.55 s |
| 전체 레벨 집계 | 4.756 → 0.522 s | 4.679 → 0.495 s | 19.15 → 2.08 s |
| 대소문자 무시 희귀 문자열 검색 | 0.277 → 0.078 s | 0.598 → 0.087 s | 1.141 → 0.306 s |
| 대소문자 무시 `한글` 검색 | 0.282 → 0.080 s | 0.589 → 0.089 s | 1.133 → 0.315 s |
| 정규식 검색 | 0.352 → 0.096 s | 0.670 → 0.105 s | 1.420 → 0.372 s |
| 레벨 E 필터 (집계 후) | 5.135 → 0.002 s | 5.126 → 0.002 s | 20.67 → 0.004 s |
| PID 필터 | 5.203 → 0.650 s | 5.184 → 0.633 s | 20.99 → 2.54 s |
| 태그 필터 | 5.332 → 0.678 s | 5.333 → 0.668 s | 21.45 → 2.70 s |
| 검색어 + 레벨 W·E 복합 | 5.434 → 0.700 s | 5.705 → 0.688 s | 21.83 → 2.74 s |

- **스캔 스레드 수:** 512 MiB LF 기준 필드 필터는 1스레드 1.78–2.07 s, 2스레드 1.11–1.22 s, 4스레드 0.63–0.70 s, 8스레드 0.87–0.93 s였고, 텍스트 검색은 각각 0.28–0.36 s, 0.16–0.19 s, 0.08–0.10 s, 0.08–0.10 s였습니다. 8스레드가 4스레드보다 오히려 느려져 텍스트 스캔 워커 상한을 4개로 고정했습니다(1스레드 기준 5.0 → 1.8 s 단축은 파서 최적화 효과, 나머지는 병렬화 효과).
- **의미 동등성:** 경계 사례 합성 파일 40만 행(LF/CRLF/단독 CR, 손상 UTF-8, 줄 번호 포함 행, 다중 태그, 빈 행·미인식 행, 줄 번호 인식 옵션 3종, 필터 20종)과 512 MiB LF·CRLF 파일에서 건수·상태·스캔 바이트·페이지 조회 결과를 대조해 차이 0건을 확인했습니다.
- **취소·닫기·메모리:** 쿼리 취소·교체 지연은 최대 0.1 ms, 양쪽 pane 스캔 중 파일 닫기(Close)는 8.3 ms였습니다. 백엔드 프로세스 peak memory footprint는 6.67 MB에서 8.68 MB로 소폭 증가했습니다(WebView 제외).
- **블록 읽기 직렬화:** `Source::read`는 읽기 도중 Close로 핸들이 닫히는 것을 방지하고 읽기 전후 파일 변경 확인(`symlink_metadata` 및 핸들 메타데이터)을 수행하기 위해 파일 핸들 Mutex를 유지합니다. 병렬화되는 구간은 블록을 읽은 뒤의 디코딩·매칭·파싱이며, 잠금을 거친 128 KiB 블록 읽기 처리량은 13.7 GB/s였습니다.
- **Windows 가설(미측정):** Windows에서는 블록마다 수행하는 경로 기준 메타데이터 조회가 핸들 열기·닫기 비용을 유발해 잠금 대기 시간이 길어질 수 있고, 단일 동기 파일 핸들의 I/O가 OS 수준에서 직렬화될 수 있습니다. 측정 방법과 macOS 기준값은 [Windows 수동 점검](#windows-수동-점검) 절에 정리되어 있습니다.

### 일치하는 줄이 없는 조건(0건 조건) 확인 및 다중 시간 조건 최적화

- **0건 조건 확인(`zero-conditions`):** 상단 pane 쿼리에서 각 조건의 일치 행 존재 여부(`some`/`none`)를 판정할 때, 메타데이터 표로 확정되는 조건은 쿼리 완료 직후(수십 ms 이내)에 확정됩니다. 시간 조건처럼 블록 스캔이 필요한 0건 조건은 쿼리 완료 후 남은 블록을 한 번 더 합동 스캔하며, 한 번 확정된 결과는 데이터셋에 캐시되어 같은 필터를 다시 적용하면 2 ms 이내에 즉시 반환됩니다. 쿼리 교체 지연 차이는 최대 0.6 ms(0.3–2.3 ms), peak RSS 증가는 약 2–3 MB 수준입니다.
- **다중 시간 조건 파싱 공유(`time-predicate`):** 한 행에 대해 여러 시간 조건이 각각 시각 문자열을 반복 파싱하던 것을 행당 1회 파싱 및 무할당(zero-allocation) 구조로 개선해, 2 GiB 로그에서 시간 조건 32개 쿼리 완료 시간이 8.23–9.38 s에서 3.25–3.37 s로 약 2.5–2.8배 단축되었습니다.

## 실시간 따라가기 (`follow`)

2 GiB(18,823,021행) 단일 텍스트 로그를 열어 상단 레벨(W·E) 필터와 하단 희귀 문자열 검색을 걸어 둔 상태에서, 파일 끝에 1 MiB 및 100 MiB를 추가할 때 증분 따라가기와 전체 다시 열기를 비교한 결과입니다(M5 Pro, 폴링 간격 1 ms로 설정해 순수 처리 시간 측정).

## Mac OS Roman 깨진 문자 복원

iOS 로그 파일의 표시 텍스트 디코딩(`encoding::decoded`)에 깨진 문자 복원을 적용하기 전후의 측정 결과입니다(Apple M4 Mac mini 10코어 16 GiB, Rust 1.99.0, warm 캐시). Android 로그와 DLT는 복원하지 않으므로 기존과 같습니다.

**블록 디코딩 단독(64 MiB, 128 KiB 블록, 1스레드, 기존→복원, 7회 중 최소):**

- `field-filters-gen` 한글·이모지 로그: 5.9 → 8.4 ms
- iOS 행마다 `“ ” … → · ─ ※` 문장부호를 넣은 로그: 9.2 → 21.5 ms
- 한글·이모지를 모두 Mac OS Roman으로 깨뜨린 로그: 7.5 → 43.7 ms
- 한글을 `café “x” – 5 °C … Grüße → ✓ «ok»`로 바꾼 로그: 8.8 → 23.3 ms

**엔진 검색(`multi-file` 벤치마크, 4 워커, 기존 커밋과 별도 프로세스로 번갈아 3회 실행한 중앙값):** `field-filters-gen` 256 MiB에서 iOS 행만 뽑아 3번 이은 파일과 그 변형을 사용했습니다.

| 입력 | 희귀 문자열 (기존→복원) | 대소문자 무시 `한글` (기존→복원) | 정규식 (기존→복원) |
| --- | ---: | ---: | ---: |
| iOS 한글·이모지 (305 MB) | 37 → 41 ms | 42 → 47 ms | 35 → 43 ms |
| iOS + 행마다 문장부호 7개 (389 MB) | 48 → 72 ms | 58 → 84 ms | 52 → 77 ms |
| iOS 한글·이모지 모두 깨짐 (346 MB) | 41 → 102 ms | 37 → 115 ms | 44 → 103 ms |
| Android 2 : iOS 1 혼합 (268 MB, 복원 대상 아님) | 32 → 32 ms | 32 → 32 ms | 34 → 34 ms |

- 인덱싱 완료, 첫 페이지 응답, 태그 필터(메타데이터 표 사용), peak memory footprint(12.1–18.1 MB)는 측정 오차 범위에서 같았고, 레벨·필드 분석 완료는 iOS 입력에서 약 0–7% 늘었습니다.
- 모두 깨진 파일에서 `한글` 검색 결과는 0건에서 2,388,747건이 되었습니다.
- iOS 파일 판별(`parser::ios_log`)은 파일당 앞 64 KiB를 파싱하는 데 0.25 ms가 걸립니다(첫 호출은 정규식 컴파일 포함 1.5 ms).
- 복원 비용은 후보 문자(`“ … → ·` 등, UTF-8 첫 바이트 `C2`·`C3`·`C5`·`C6`·`E2`·`EF`)당 약 8 ns입니다. 후보가 없는 블록은 `memchr` 두 번으로 건너뛰고, 후보가 가까우면 문자 단위로, 멀면 `memchr`로 다음 후보를 찾습니다.
- **한계:** 문장부호가 매우 많은 iOS 로그는 검색할 때마다 이 비용을 다시 냅니다. 블록별 복원 필요 여부를 첫 스캔 뒤 기억하면 줄일 수 있지만 구현하지 않았습니다.

Apple M4 Mac mini(macOS 27.0.1)에서 Android Studio의 에뮬레이터(AVD `Medium_Phone_API_37.0`, Android 37, arm64, Google Play 이미지)와 adb 1.0.41(Platform-Tools 37.0.1)로 확인했습니다. 실기 테스트(`core/tests/capture_device.rs`)는 제품의 adb 연결을 그대로 쓰며, 기기에서 직접 찍은 확인용 줄(`log -t`)로만 판정합니다.

| 확인 항목 | 관찰 |
| --- | --- |
| 출력 줄바꿈 | LF만 사용(CR 0바이트, adb `shell,v2`) |
| `logcat -T 'MM-DD hh:mm:ss.mmm'` | 그 시각의 줄을 포함하고 더 이른 줄은 내보내지 않음. 버퍼마다 `--------- beginning of …` 줄을 함께 출력 |
| 실행 중인 `adb logcat`이 끝날 때 | adb 서버 종료·기기 재부팅 모두 종료 코드 255, 오류 출력 없음(원인 구분 불가) |

| 부팅 직후 | 기기가 잠시 `offline`이 되었다가 다시 연결됨 |
| 같은 줄 반복 | 기기가 같은 밀리초에 똑같은 줄을 여러 번 남기기도 함(그래서 중복 여부는 기기 버퍼에 있는 같은 줄의 개수와 비교해 판정) |

| 시나리오 | 결과 |
| --- | --- |
| 기록 시작 경계 | 시작 뒤 찍은 확인용 줄 100개가 각각 한 번씩 기록되고, 시작 전에 있던 줄은 0개 |

- 화면 동작(기기 메뉴, 기록 상태, 끊김·재연결 표시, 저장 확인, 남은 기록)은 QA 빌드의 가짜 기기로 실제 macOS WKWebView에서 검증했습니다(`tests/e2e` `devices` 시나리오).
- 기록이 표시까지 걸리는 시간과 장시간·고속 기록의 처리량은 아직 측정하지 않았습니다. 표시 지연은 따라가기의 폴링 주기(0.5초)에 묶여 있습니다.

- 초당 줄 수는 그때 기기가 남기는 로그 양에 따라 달라지므로, 위 숫자를 USB 결과와 비교해 Wi-Fi가 느리다거나 줄이 빠졌다고 판단할 수는 없습니다. Wi-Fi에서 줄이 빠지는지는 확인하지 않았습니다.
- USB와 Wi-Fi로 함께 보이는 기기에서 USB를 고르는 동작은 단위 테스트로만 확인했습니다.
- 목록에는 있지만 연결 요청에 답하지 않는 Wi-Fi 기기는 가짜 Apple 기기 서비스로 확인했습니다. 그런 기기 2대가 약 3초 만에 `offline`으로 담기고, 목록 요청 전체는 실패하지 않았습니다. 실제 기기가 이렇게 답하지 않는 상황이 생기는지는 확인하지 않았습니다.
- Wi-Fi를 끄면 Apple 기기 서비스가 연결을 닫아 기록이 대기 상태로 넘어갔으므로, 데이터가 오지 않을 때 끊긴 것으로 보는 별도 시간 제한은 두지 않았습니다.
- 기록하지 않는 동안 잠긴 iPhone이 목록에서 사라졌다가, 잠금을 풀자 다시 나타났습니다.

### 개발용 서명 앱 실행 (`OS_ACTIVITY_DT_MODE`)

Apple M4 Mac mini(macOS 27.0.1, Xcode 27.1, `devicectl` 651.13.5)에서 Wi-Fi로 연결한 같은 iPhone 16 Pro(iOS 27.0.1)로 확인했습니다. 대상 앱은 사용자가 Xcode로 설치한 개발용 서명 앱이며, 기기 로그와 앱 이름·bundle ID는 저장소에 남기지 않았습니다.

| 항목 | 결과 |
| --- | --- |
| 앱 목록(`developer_builds_are_listed`) | Xcode 확인을 포함해 0.59초. 사용자 앱 5개 중 `get-task-allow` 앱 3개만 담김. 같은 기기에서 `devicectl device info apps`의 `builtByDeveloper`는 App Store 앱 2개를 포함한 5개 모두 `true` |
| 기록 중 다시 실행(`a_developer_build_started_again_logs_its_private_values`) | `devicectl` 실행 0.5초. 이후 10초 동안 그 앱 프로세스 18,152줄 중 `<private>` 0줄, 다른 프로세스는 `<private>` 12,097줄 그대로 |
| QA 빌드(가짜 기기 없음)에서 실제 기기로 앱 실행 | 기록 중 `앱 실행…` 표시 → 메뉴에 개발용 서명 앱 3개(0.54초) → 앱 선택부터 완료 알림까지 1.71초 → 약 8초 뒤 기록 중지. 다시 실행된 앱 프로세스 18,152줄 중 `<private>` 0줄, 다른 프로세스 87,618줄 중 `<private>` 27,628줄 |
| 같은 경로에서 기기가 잠겨 있을 때 | 약 10.7초 뒤 실패. `devicectl`의 최상위 오류는 "The application failed to launch."뿐이고 잠김 이유는 중첩된 `NSUnderlyingError`(`FBSOpenApplicationErrorDomain` 7, `Locked`)에 있어, 잠김을 알아보고 아래쪽 오류의 실패 이유를 쓰도록 고침 |

- `OS_ACTIVITY_DT_MODE` 없이 실행했을 때는 앞서 같은 방식으로 기록한 측정치(그 앱의 `<private>` 3,519줄)를 비교 기준으로 삼았고, 이번에 다시 재지는 않았습니다. `--console`만 주었을 때는 `<private>`가 그대로 가려졌습니다.
- 위 실기기 확인 뒤에 실행 지점 표시, 실행 중 포커스 유지, 상단 바 문구 순서 변경을 더하고, 실시간 따라가기로 목록이 스크롤될 때 상단 바 메뉴가 닫히지 않도록 고쳤습니다. 이 변경은 가짜 기기 e2e와 단위 테스트로만 확인했고, 실기기에서는 다시 확인하지 않았습니다.
- 기기 재부팅 직후처럼 개발자 디스크 이미지가 마운트되지 않은 상태의 첫 실행 시간, USB 연결, iPad, iOS 17–26, Xcode가 없는 Mac과 첫 실행 설정이 끝나지 않은 Xcode(`xcodebuild -checkFirstLaunchStatus` 실패), Xcode가 Wi-Fi로 연결하지 못하는 기기(`CoreDeviceError` 1000, 합성 JSON으로만 확인), App Store 앱에 이 변수를 넘겼을 때의 동작은 확인하지 않았습니다.

## 기능별 검증 요약

- **앞쪽 줄 번호 자동 인식:** 혼합 Android/iOS·Unicode·CR/LF/CRLF·일반 숫자 문장·모호한 iOS 줄에 대해 자동·켜기·끄기 동작과 필터·통계·페이지 일치를 Rust 및 Node 테스트로 검증했습니다.
- **손상된 UTF-8 처리:** 다중 바이트 문자 중간 잘림(CRLF·청크 경계·EOF), 연속 손상 바이트, 원본 `U+FFFD` 문자와의 구분, 검색 하이라이트 UTF-16 오프셋 일치, 400 KB 원문 상세의 바이트 위치 탐색을 Rust 테스트로 검증했습니다.
- **Mac OS Roman 깨진 문자 복원:** Rust 테스트로 다음을 검증했습니다.
  - 한글·이모지·따옴표·키릴 단어는 복원하고, 원래 있던 악센트·기호(`l’école`, `“école”`, `20 °C` 등)와 Windows-1252로 깨진 문자열, 줄 구분 문자가 생기는 경우는 그대로 둡니다.
  - 잘린 구간, 손상 바이트가 섞인 행의 손상 표시, 무작위 텍스트 2만 건의 왕복과 행 경계, 무작위 바이트 퍼징
  - iOS 파일 판별(Android 파일, 합쳐 연 파일별 판단, 붙여넣기)과 엔진의 문자열·정규식 검색, 강조, 태그 필터, 원문 상세, 내보내기 원본 유지
- **클립보드 및 네이티브 기능:** macOS 네이티브 클립보드 테스트는 격리된 named pasteboard와 합성 URL만 사용해 시스템 클립보드를 오염시키지 않습니다. 행 번호 열 자동 폭 확장, 트랙패드 핀치 배율 조절, 창 위치·크기 복원은 Node·Rust 단위 테스트 및 실제 macOS WKWebView E2E 테스트로 검증했습니다.
- **DLT 디코더 정확성:** COVESA 공개 샘플(`tests/fixtures/covesa`) 111개 메시지와 무작위 스트림 300회 분할 테스트, 독립 파서 `dlt_parse` 0.10.1과의 메시지 3,000개 대조 테스트로 검증했습니다.

## Windows 수동 점검

Windows 환경에서는 CI 자동 빌드·단위 테스트만 실행하고 실제 GUI 화면은 직접 확인하지 않았습니다. Windows PC에서 빌드를 검증할 때는 아래 항목을 순서대로 점검합니다.

1. **초기 실행 및 WebView2:** 첫 실행 시 1280×820 창이 주 모니터 중앙에 열리고 한글·이모지가 정상 표시되는지 확인합니다.
2. **파일 선택(`Ctrl+O`):** 단일 파일 및 다중 파일(`Ctrl`/`Shift` 선택) 열기, 병합 순서, `파일 · 행` 배지와 파일 경계선을 확인합니다.
3. **드래그 앤 드롭:** 파일 탐색기에서 단일·다중 파일을 끌어다 놓을 때 드롭 안내 표시와 열기 동작을 확인합니다(폴더·바이너리 파일 드롭 시 오류 안내 확인).
4. **클립보드 붙여넣기(`Ctrl+V`):** 로그 텍스트 붙여넣기로 새 로그 열기 및 검색 입력란 내 일반 붙여넣기 동작을 확인합니다.
5. **화면 배율:** `Ctrl` + `+`/`-`/`0`, `Ctrl+마우스 휠`, 터치패드 핀치 제스처 동작과 재실행 시 배율 복원을 확인합니다.
6. **내보내기:** CRLF 원본의 줄바꿈 유지 여부, 취소 시 임시 파일 정리 여부, 현재 열려 있는 파일 덮어쓰기 방지 동작을 확인합니다.
7. **최근 파일 및 작업 복원:** `%APPDATA%\dev.logstudio.desktop` 하위 설정 파일(`recent-files.json`, `work-states.json`, `saved-filters.json`, `window-state.json`) 생성과 재열기 복원을 확인합니다.
8. **대용량 파일(2 GiB 이상):** 읽는 중 `읽기 취소`, `파일 닫기`, 첫 행 표시 시간과 작업 관리자 메모리 점유율, 끝부분 7–8자리 행 번호 표시를 확인합니다.
9. **다크 모드 및 다중 모니터:** Windows 다크·라이트 테마 전환과 배율이 다른 모니터 간 창 이동·최대화 복원을 확인합니다.
10. **실시간 따라가기:** 외부 프로그램이 기록 중인 파일을 동시에 열어 따라가기가 정상 동작하고 외부 프로그램의 쓰기·이름 변경이 차단되지 않는지 확인합니다.

**읽기 잠금 성능 점검 (`read-lock`):** Windows에서 블록 읽기 경로의 메타데이터 확인 비용을 측정하려면 아래 명령을 실행합니다.

```powershell
cargo run --release --locked -p logstudio-bench --bin read-lock -- 512 $env:TEMP\logstudio-bench 2 > bench-windows.txt
```

```sh
cargo run --release --locked -p logstudio-bench --bin read-lock -- 512 /tmp/logstudio-bench 2 | tee bench-macos.txt
```
